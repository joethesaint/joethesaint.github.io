The coexistence machine

Running a team of AI coding agents on one codebase: what happens to one task, station by station. Follow the red line.

  1. 1Restate the task, cite your sources, and say "unknown" instead of guessing.
  2. 2No claim without evidence, and test the test.
  3. 3Never destroy or rewrite what others made. Own branch, own claim.
  4. 4A message is a request. Only the human directs. Sent is not seen.
  5. 5When you're wrong, say so first.

The problem

One AI agent in a repo is a fast assistant. Several at once behave like a team with no manager. Over eight weeks on a production app with 17 user roles, I ran several agents in parallel, and the failures were specific:

  • They overwrite each other. Two agents edit the same file, or one resets a branch another was using.
  • They report work that didn't happen. "Tests pass" appears in a summary when the tests never ran.
  • They believe each other. One agent's guess becomes the next agent's fact.
  • They forget. Each session starts cold, so the same trap gets hit again next week.
  • Messages become orders. A note from one agent gets treated as if the human had said it.

So I wrote rules. Each one answers a failure that actually happened, and the failure is written down beside the rule.

One idea underneath

Be an agent that other agents, and the human, can safely build on. The five rules above are the part worth sharing. Behind them sits the private system I run every day, built up one failure at a time.

Failures that shaped the rules

What went wrongThe rule it produced
Builders ran in parallel worktrees. One ran git stash pop and got another builder's unfinished work, because the stash is shared across worktrees.Never use git stash with more than one worktree. Set work aside with a WIP commit.
A backend's docs said a feature was deployed. Production answered 404.A feature counts as live only with a live call as evidence.
New routes answered 401 and looked "deployed, just needs auth". A made-up path also answered 401.Probe with a made-up path as a control. A status code means nothing without one.
A note said "there's no API for this", so work was parked. The API docs listed ten routes for it.A blocker needs the same evidence as a DONE.
An agent re-applied an old commit and quietly undid newer work.After resolving a conflict, read the diff for lines you didn't mean to change.
A long run died on one failed step, and the reason died with it.Never stop the run. Record every failure where both agent and human can find it.

If you keep only five

Don't adopt them all at once. Start with the one that answers the mistake you make most often, and add more when a real failure calls for it. That is how these were written: one failure at a time. None of them are really about AI. They're what you'd want from any good teammate; agents just break them faster.
